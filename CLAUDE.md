# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Multi-Agent Hub: an open-source (MIT) Windows desktop app that runs Claude Code, Codex and a local Ollama model as parallel agent sessions on different projects, with automatic handoff to the next agent when one hits a usage limit. `docs/plan.md` is the confirmed plan (requirements, tradeoffs, build phases 1–10; phase 10, design styles and layouts, comes before phase 6, iPhone access, which comes last). `docs/progress.md` holds per-session recaps and the current next steps; read it first to see where work stopped, and append a new recap at the end of each session.

Phases 1–3 are done (Claude and Codex sessions, handoff, React UI in `frontend/`). Phase 4 is split into 4a–4d in `docs/plan.md`: 4a (runner interface, per-session git worktrees) is done; 4b is done (dashboard, progress view, history and summaries; manual checks in `docs/TODO.md`); 4c (style polish) is done (4c-1: `MarkdownText` with `remark-gfm` and `rehype-highlight`, token colors as `--hl-*` theme variables; 4c-2: edit diffs, command rows, turn-end rows, per-file edit history; 4c-3 and 4c-4: per-agent colors, composer, markdown typography, light and narrow fixes; plus a System/Light/Dark switch in Settings: `theme.ts` sets `data-theme` on `<html>`, and the light tokens live under `:root[data-theme="light"]`). Agent colors: `--agent-claude/codex/ollama` theme tokens; an `agent-<kind>` class (`agentClass` in `AgentBadge.tsx`) sets `--agent` for everything inside it, so style agent-tinted parts with `var(--agent)`, not `--accent`; 4d (Tauri shell, `frontend/src-tauri`) is done. Phase 5 (local model) is split into 5a–5d in `docs/plan.md` and uses the hub's own agent loop on Ollama's HTTP API (Codex CLI with `--oss` was tested and rejected); 5a (chat adapter), 5b (tools and loop) and 5c (context budget, loop detection, default local model, notices) are built; 5d (OpenAI-compatible runtimes) is on hold. Revisions between phases are added to `docs/plan.md` after the last completed phase, not by rewriting phases: the session-flow revision and revision 2 (model picker and reasoning effort) are built; revision 3 (skills, slash commands and tools) is built on `revision/skills`; phase 7 (delegation) is next. Revision 6 (CI/CD, releases, open-source pass) is merged; revision 7 (terminal-level agent access) is planned. The project is becoming open source (MIT), for anyone to run with their own CLI logins.

**Branches (see `RELEASING.md`):** feature branches merge into `staging` through pull requests, never into `main`. CI (`.github/workflows/ci.yml`: Windows backend tests, UI typecheck and build, version check) must pass, and a passing push to `staging` fast-forwards `main` to it. Releases are tags `vX.Y.Z` on `main` (`.github/workflows/release.yml`). Add user-visible changes under Unreleased in `CHANGELOG.md`. Claude and Codex are driven through their official CLIs under the user's own logins; the app must never read or store login tokens. The local model needs no sign-in.

## Commands

All from `backend/`, using `uv` (Python 3.14 pinned in `.python-version`, exact versions in `uv.lock`; commit `uv.lock`):

```powershell
uv sync                                          # install
uv run python -m app.main                        # run API on http://127.0.0.1:8765 (docs at /docs)
$env:HUB_RELOAD="true"; uv run python -m app.main   # dev auto-reload
$env:HUB_SIMULATE_LIMIT="claude"; uv run python -m app.main   # dev: Claude's turns end in a fake usage limit (try handoff)
uv run pytest                                    # all tests
uv run pytest tests/test_claude_adapter.py::test_name   # single test
$env:HUB_LIVE_CLAUDE="1"; uv run pytest tests/test_claude_live.py  # opt-in, uses real claude CLI + subscription usage
$env:HUB_LIVE_CODEX="1"; uv run pytest tests/test_codex_live.py    # opt-in, uses real codex CLI + ChatGPT Codex allowance
$env:HUB_LIVE_OLLAMA="1"; uv run pytest tests/test_ollama_live.py  # opt-in, uses the local Ollama server (free)
uv run alembic revision --autogenerate -m "describe change"  # after editing app/models.py; review the file
uv add <pkg> / uv add --dev <pkg>
uv run pyinstaller hub-backend.spec --noconfirm  # bundle for the desktop app -> dist/hub-backend/
uv run python scripts/snapshot_release_db.py 0.2.0  # at release: sample DB dump for the upgrade tests
uv run python ../scripts/version.py check        # every file has the same version (also: set X, notes X)
```

Desktop app, from `frontend/` (Rust in `%USERPROFILE%\.cargo\bin`): `npm run tauri dev` (backend from source via `uv run`, Vite hot reload), `npm run tauri build` (PyInstaller bundle, UI, NSIS installer in `src-tauri/target/release/bundle/nsis/`).

Settings are `HUB_*` env vars or `backend/.env` (`HUB_DATABASE_URL`, `HUB_HOST`, `HUB_PORT`, `HUB_RELOAD`, `HUB_LOG_LEVEL`, `HUB_CORS_ORIGINS`, `HUB_WORKTREES_DIR`, `HUB_CHATS_DIR`, `HUB_TOKEN_FILE`, `HUB_TOKEN`, `HUB_LOCK_FILE`, `HUB_OLLAMA_URL`, `HUB_OLLAMA_MODEL`, `HUB_OLLAMA_NUM_CTX`, `HUB_OLLAMA_THINK`, `HUB_OLLAMA_MAX_ROUNDS`, `HUB_OLLAMA_COMMAND_TIMEOUT`, `HUB_LOCAL_DIR`). All app data lives in `%LOCALAPPDATA%\MultiAgentHub` (`data\hub.db`, `data\token`, `worktrees`, `chats`, `local`, `logs`), shared by `uv run` and the desktop app; `app/server.py` holds `data\server.lock` while a backend runs, so a second one exits with code 3.

## Architecture

- **App factory** (`app/main.py`): `create_app(engine=None)` builds the app; tests pass an in-memory `StaticPool` SQLite engine. Lifespan runs `init_db`, which applies Alembic migrations to `head` on every start, so there is no `create_all`. Schema changes always need a migration.
- **DB** (`app/db.py`, `app/models.py`): SQLModel on SQLite with foreign keys, WAL and busy_timeout set per connection. Tables: `sessions` (`AgentSession`: title, folder, status, optional per-session `chain` and `limit_policy`), `stints` (`Stint`: one agent's turn at a session with agent, model, reasoning `effort` (migration `b7e41c2d9a10`; low/medium/high/xhigh/max or None for the CLI default, sent as Claude's `--effort` or Codex's `-c model_reasoning_effort` on every turn, not on summaries; `PATCH /sessions/{id}` `effort` changes the current stint's from the next turn via `Orchestrator.set_effort`; handoff and create take it too), native session id, `reason` new/limit/manual/delegation, optional `parent_stint_id` reserved for phase 7, and the `brief` it started from), `events` (`SessionEvent`, with `stint_id`) and `settings` (key/JSON value, `HubSettings`: `chaining_enabled`, `default_chain`, `limit_policy` (the default for each chat's Auto handoff switch), `default_agent`/`default_model`/`default_effort` for new chats (`default_effort`, default medium, is applied by `stint_effort()` wherever `stint_model()` is, so automatic handoffs get it too; none for the local model; the picker has no "Default" effort), `progress_layout`, `local_model`). Child rows use `ON DELETE CASCADE`. The current stint is the latest by `seq` (`current_stint`); the API's `SessionRead` (`session_read`) exposes its agent, model and native id plus the stint list. Enums are stored by **value** as plain text with no CHECK constraint (`enum_column`), so adding a member needs no migration. Migrations use `render_as_batch=True` for SQLite, but **never batch-rebuild `sessions` or `stints`**: with foreign keys on, dropping the old table cascades and deletes child rows. Use plain `ALTER TABLE ADD/DROP COLUMN` (see the stints migration). Autogenerate reports a false `events.stint_id` FK change (SQLite reflection misses inline `ON DELETE`); drop it from generated files. `migrations/env.py` uses the connection passed in by `init_db` when there is one, and otherwise the settings URL (CLI). Before a pending migration, `init_db` copies a file database to `data\backups` (`backup_before_migrating`, SQLite backup API, last 5 kept). Released schemas have dumps in `tests/release_dbs/`; `test_release_upgrades.py` upgrades each to head checking no rows are lost, and fails on a migration that batch-rebuilds `sessions`/`stints` or drops a history table.
- **Adapter interface** (`app/adapters/base.py`): one `AgentAdapter` instance per session, constructed with its cwd and model. `start_task` and `send_reply` return async iterators of normalized `AgentEvent`s (`EventType`). A usage limit is a `LIMIT_REACHED` **event**, not an exception, and handoff will key off it. The orchestrator, UI and history should depend only on this interface.
- **Claude adapter** (`app/adapters/claude.py`): one `claude -p --output-format stream-json --verbose` process per turn, with the prompt sent over **stdin** (this avoids Windows quoting). Replies use `--resume <session id>`. `--permission-prompts none` means unapproved tools are denied rather than left hanging. AskUserQuestion is unavailable headless, so an appended system prompt makes Claude end question turns with `[[NEEDS_INPUT]]`, which `TurnParser` turns into a `QUESTION` event. `rate_limit_event` with status `rejected` is the main limit signal; regex on the result text is the fallback. `stop()` kills the whole process tree (`taskkill /T`). It refuses `.cmd`/`.bat` shims and requires the native `claude.exe`. Behavior was verified against Claude Code 2.1.305.
- **Runner** (`app/adapters/runner.py`): every CLI launch goes through a `Runner` (`start(command, cwd, env)` returns a `RunningProcess` with `send_input`, `lines`, `read_stderr`, `wait`, `kill`). `HostRunner` (the default) runs a local process and kills its tree with `taskkill /T`. Phase 9's Docker runner plugs in here; adapters take an optional `runner=`.
- **Shared CLI plumbing** (`app/adapters/cli.py`): `CliAdapter` runs one process per turn through its runner, sends the prompt over stdin, streams parsed lines, adds an error if the CLI exits before reporting the end of the turn, and `stop()` kills the process tree. It also holds `NEEDS_INPUT_MARKER` / `HEADLESS_PROMPT` and the headless git env. Neither CLI has a plan tool headless, so `HEADLESS_PROMPT` asks for the plan as a markdown checklist under a `PLAN_MARKER` line, re-posted after each step; `split_plan` strips the marker from messages and both parsers turn the checklist into a `PLAN` event when it changes (`plan_items`: the first unchecked step is in progress). Both adapters subclass it.
- **Codex adapter** (`app/adapters/codex.py`): `codex exec --json -` per turn, `codex exec resume --json <thread id> -` for replies. Codex chooses the thread id and reports it in `thread.started`, so the adapter learns it from the stream and the orchestrator saves it from the `STARTED` event (Claude's id is chosen up front). Sandbox, `approval_policy="never"` and the marker instruction (`developer_instructions`) are passed as `-c` overrides, because `resume` has no `--sandbox`. `find_codex` runs the native `codex.exe` inside the npm package, never the `.cmd`/`.ps1` launchers. Exec mode never waits for approval: blocked actions fail as ordinary command errors. The stream has no rate-limit events, so after each turn `read_rate_limits` takes the plan's usage windows from the latest `token_count` in Codex's session file (`$CODEX_HOME/sessions/.../rollout-*-<thread id>.jsonl`, an undocumented format, read best effort) and emits the same `RATE_LIMIT` shape as Claude. A limit is detected from the error text. Codex reports no price, so the UI shows tokens. Verified against codex-cli 0.164.0. Settings: `HUB_CODEX_SANDBOX` (default `workspace-write`, which also allows `%TEMP%`) and `HUB_CODEX_PATH`.
- **Local model adapter** (`app/adapters/ollama.py`, phase 5a): no CLI; `OllamaAdapter` streams Ollama's native `POST /api/chat` (NDJSON) with `httpx2` (a runtime dependency) and sends `options.num_ctx` (`HUB_OLLAMA_NUM_CTX`, default 32768) on every request, because Ollama's default 4096 silently cuts longer prompts. Ollama keeps no history, so the adapter saves each conversation as `HUB_LOCAL_DIR/<uuid>.json` (default `%LOCALAPPDATA%\MultiAgentHub\local`); the uuid is the stint's `native_session_id`, chosen up front like Claude's, so replies and backend restarts resume from the file. Deleting a session deletes its files. A failed message isn't saved (so resending doesn't duplicate it); a stopped one is, with the partial reply. The request runs in its own task so `stop()` can cancel it while the model is loading or thinking. Thinking text is dropped. Errors become `ERROR` events, never `LIMIT_REACHED`. `default_adapter_factory` checks `GET /api/tags` synchronously (3 s) and raises `AgentUnavailable` when Ollama is off or the model isn't installed, so the chain skips it; `pick_model` takes the stint's model, else `HUB_OLLAMA_MODEL`, else the first installed model with the `tools` capability. `HUB_OLLAMA_URL` must be loopback. `GET /api/local/models` (`app/api/local.py`) lists installed models for the new-session dialog. Verified against Ollama 0.40.15 with `qwen3.5:9b-q4_K_M`.
- **Local model tools and loop** (`app/adapters/local_tools.py`, phase 5b): each request carries `TOOL_DEFINITIONS` (`read_file`, `list_files`, `search`, `write_file`, `edit_file`, `run_command`, `update_plan`, `ask_user`); `_turn` runs the reply's `tool_calls`, appends `{role: "tool", content, tool_name}` results and asks again until a reply calls none, up to `HUB_OLLAMA_MAX_ROUNDS` (30) requests, then ends with an `ERROR` marked `round_cap`. `update_plan` emits `PLAN` and `ask_user` ends the turn as `QUESTION` (no text markers). `LocalTools.resolve` refuses any path outside the working folder and writes inside `.git`. `run_command` writes the command to a temp `.ps1` (UTF-8 with BOM) and runs `powershell.exe -File` through the `Runner`, with a UTF-8 prefix, a suffix that passes on the program's real exit code, a timeout (`HUB_OLLAMA_COMMAND_TIMEOUT`, 300 s) and output capped by `cap`. Events reuse Claude's tool names and shapes (`Read`, `Write`, `Edit`, `PowerShell` with `file_path`/`command`, plus `List`, `Search`), with `diffs` from `diffs.hunks` and `exit_code`, so the UI needs nothing new. Errors in a call (bad JSON, unknown tool, refused path) go back to the model as tool results. `stop()` cancels the request and kills the running command. An empty final reply after tool work still completes the turn. The factory passes `tools=False` for a model whose capabilities lack `tools` (plain chat prompt, no tools sent).
- **Local model robustness** (phase 5c): `app/adapters/local_context.py` `fit()` runs before every request against `prompt_budget(num_ctx, tools)` (chars / 3; 20% or at least 4096 tokens kept for the reply) and shortens only what is sent, never the saved file: old tool outputs and old write/edit contents to stubs (the last 6 messages kept), then earlier turns' tool steps (keeping requests and final answers), then whole earlier turns, then the current turn's outputs and the middle of its message; the first user message (the task) is always kept, and the system prompt notes how many messages were left out. A `NOTICE` event (`{message, reason}`, new `EventType`, rendered as a yellow row) reports it once per turn. The same call with the same arguments a 3rd time in a row is answered with a nudge, a 4th ends the turn; that and the round cap end with `NOTICE` + `QUESTION` (`reason` `loop` / `round_cap`), so the session waits rather than fails. An empty reply after tool work gets one `QUIET_NUDGE` request (sent, not saved). The default local model is the hub setting `HubSettings.local_model`, applied by `stint_model()` when a stint is created (session create, `_handoff`, `_can_run`, summaries via `Orchestrator._with_default_model`), and reported as `default` by `GET /api/local/models`. Frontend: `ModelSelect.tsx` (`useLocalModels`, `localProblem`) is the one model picker for every dialog.
- **Model lists** (`app/model_list.py`, `app/api/models.py`): `GET /api/models` (`ModelCatalog`) gives every picker Claude's current full names (`version`, `CLAUDE_VERSIONS`, update with releases; the aliases are left out as redundant) and Codex's models from `$CODEX_HOME/models_cache.json` (`account`; only its `models` entries, never `auth.json` or `identity`; `CODEX_FALLBACK` when unreadable), each with `available` true/false/null and `efforts`/`default_effort` (Claude: all five; Codex: per model from the cache's `supported_reasoning_levels`, "ultra" left out). Availability is stored in the `settings` table under `model_availability` (not part of `HubSettings`): `Orchestrator._learn_model` records it after each turn of a stint with a chosen model (before the status is set; false only when the error matches `UNAVAILABLE_MODEL`), and `POST /api/models/check` (`Orchestrator.check_models`) sends each model a tiny `summarize` call in an empty temp folder (4 at a time, limits and other errors are "unknown", never "refused"). `create_app(codex_home=)` keeps tests off the real `~/.codex`; fake Claude has a `badmodel` mode. Frontend: `useModelCatalog()` in `ModelSelect.tsx` shares one copy between pickers (offline fallback `MODELS`), with optgroups, disabled "(not on your plan)" options and **Other…**. The composer's `ModelPicker` (`ComposerControls.tsx`, beside Send, logos in `AgentLogo.tsx`) is one box with a three-column menu: provider, model, effort.
- **Skills** (`app/skills.py`, `app/api/skills.py`, revision 3): a skill is a folder with a `SKILL.md` (YAML frontmatter `name`, `description`), the format both CLIs load. The hub library lives in `HUB_SKILLS_DIR` (default `%LOCALAPPDATA%\MultiAgentHub\skills`): `library.json` (per skill: `source` link/copy, `path`, a switch per agent, `origin` when it lives in a CLI's own folder, `repo`/`commit`/`subpath` for git), `library/<name>` (copies from git or zip), `views/claude` (a Claude plugin named `hub` whose `skills/` are **junctions** to the skills on for Claude; rebuilt on every change; never delete through a junction, `_remove_link` uses `rmdir`), `staging/<id>` (downloads waiting for review, kept an hour). Folders on this PC (including the user's own Claude or Codex skills) are linked, git and zip are copied; `read_skill` suggests switches (off for other agents when a skill names one CLI's tools, off for Local when it has scripts). Delivery: Claude `--plugin-dir views/claude` (skills show as `hub:<name>`); Codex `developer_instructions` += `library.instructions()` (name, description, absolute `SKILL.md` path; Codex reads it with a shell command, as it does its own skills); local model the same list in its system prompt plus `LocalTools.read_roots` (read, never write). An agent isn't given a library skill from its own folder (`origin`). `Orchestrator.send` runs `expand_command` on the prompt only (the transcript keeps what was typed): a library skill becomes `/hub:name` for Claude and the skill's body plus folder in front of the request for Codex and the local model; a Codex skill of its own becomes `$name`. The `/` menu (`GET /api/skills/commands`, `menu()`): Claude's own skills from the `init` stream event, recorded after every turn under the `agent_capabilities` setting (`TurnParser` adds `capabilities` to `STARTED`, the orchestrator pops it before saving), or with none yet from `probe_claude`, a run of `/context` that makes no model request; Codex's from `codex app-server` `skills/list` (JSON-RPC over stdio, 30 s cache, never reads `auth.json`); plus library skills on for the agent, `CLAUDE_BUILTINS` (only `/context` and `/usage` work headless and aren't covered by hub controls) and `HUB_COMMANDS` (listed first, only for an open session). Hub commands: `Orchestrator.send` catches `/compact [focus]` (`hub_command`) for every agent before anything is saved or sent and runs `_run_hub_command`: a `_handoff` to the same agent, model and effort with `wait` and `build_brief(compact=True)`, whose focus text is the note; the `handoff` event carries `command`, which the transcript shows as "Conversation compacted" (revision 4 moves Claude and Codex to their own documented compaction). There is no `/clear`: the user decided it is redundant in the hub (a new chat does the same). Before the first message it saves a `NOTICE` instead. Imports never run anything: `clone` is `git clone --depth 1 --no-recurse-submodules` with hooks off; `extract_zip` refuses paths outside its folder and archives over 50 MB. Windows note: a folder made by `tempfile.mkdtemp` (Python 3.13+) is owner-only, which Codex's sandbox can't read, so the library and staging use plain `mkdir`. Tests: `create_app(skills_dir=, claude_home=, discover_native=False)`; `conftest` also sets `HUB_SKILLS_DIR` to a temp folder. Frontend: `SkillsDialog.tsx` (Skills button in the sidebar), `SlashMenu.tsx` in `Composer` (`loadCommands`, `commandsKey`), and `usedSkill` labels Skill tool calls and `SKILL.md` reads as "Used skill" rows.
- **Diffs** (`app/adapters/diffs.py`): an edit's `TOOL_RESULT` carries `diffs: [{path, kind add|update|delete, diff, base, truncated}]`, where `diff` is unified hunks with no file header (capped at 40k characters) or None when unknown. Claude's come from the `structuredPatch` (or a create's content) in the stream's `tool_use_result`. Codex's come from `FileSnapshots`: `CodexAdapter._on_event` (async, a `CliAdapter` hook) reads each patched file after `item.completed` and diffs it against the copy it kept after the previous patch, or against `HEAD` the first time (`base: "commit"`), in memory per adapter. Codex command results also carry `exit_code`. The UI (`frontend/src/diffs.ts`, `DiffView.tsx`) rebuilds diffs without line numbers from Claude's input for events saved before this, and reads Claude's exit code from the `Exit code N` line its results start with.
- **Auth** (`app/auth.py`): every `/api` router is included with `Depends(require_caller)`, which checks `Authorization: Bearer` against the per-install token (`%LOCALAPPDATA%\MultiAgentHub\data\token`, created in the lifespan, ACL'd to the current user; `HUB_TOKEN` replaces it) with `secrets.compare_digest` and returns a `Caller`. `HostOriginMiddleware` (outermost) rejects non-loopback `Host`, unknown `Origin`, and `Sec-Fetch-Site: cross-site`. `HUB_HOST` must be loopback. In the browser the Vite proxy injects the token, so the page never holds it and `EventSource` still works. In the desktop app the UI holds it: `frontend/src/connection.ts` gets `{base_url, token}` from the shell's `hub_connection` command, `apiFetch` adds the header, and `openEventStream` reads SSE with `fetch` (reconnecting with `Last-Event-ID`); `http://tauri.localhost` is in the default `cors_origins`.
- **Desktop shell** (`frontend/src-tauri/src/lib.rs`): on launch picks a free loopback port and a new random token, starts the backend (`uv run python -m app.main` in debug builds, the bundled `resources/backend/hub-backend.exe` in release, or `HUB_BACKEND_EXE`) with `HUB_TOKEN`/`HUB_PORT` in its env and no window, output appended to `logs\backend.log`. A supervisor thread polls `/api/health` (raw HTTP) to report `ready`, and restarts the backend when it exits (backoff, gives up after more than 5 crashes in 2 minutes, or at once on exit code 3), emitting `backend-status` events that `BackendBanner.tsx` shows (with Retry → `restart_backend`). Each run is put in a kill-on-close job object (`job.rs`), so a crash or the shell closing also kills the agent CLIs it started. `tauri-plugin-single-instance` focuses the open window instead of starting a second app. Tests use `make_client` in `conftest.py` (loopback `base_url` plus `TEST_TOKEN`); `create_app(..., token=)` skips the file.
- **Tests**: `tests/fake_claude.py` and `tests/fake_codex.py` stand in for the CLIs (modes `ok`, `question`, `crash`, `hang`; Codex also `tools`, `limit`) and are injected via `command=[sys.executable, FAKE_..., mode]`. `conftest.fake_adapter_factory(session, stint, cwd)` picks the fake by the stint's agent and the mode from the session title, either one mode (`ok`) or per agent (`claude:limit codex:ok`). The local model is unavailable (`AgentUnavailable`) unless the title gives it a mode (`ollama:ok`), so chains ending in it behave as when Ollama is off; then `tests/fake_ollama.py` (`FakeOllama(mode).transport`, an `httpx2.MockTransport`; modes `ok`, `hang`, `empty`, `missing`, `error`, `midstream`, `down`, `tools`; `FakeOllama(script=[...])` replays tool calls, picked by position since the last user message so a fresh instance per turn follows it; `.calls` records request bodies) stands in for the server. `create_app` takes `local_dir`, `ollama_url` and `ollama_transport` for tests. Tests that use the real factory must point `ollama_url` at a closed port, or they reach the user's real Ollama. Fake Claude also has a `limit` mode and echoes its cwd. The `client` fixture puts worktrees in a temp folder; `test_worktrees.py` builds a real temp git repo. Live tests are opt-in: `HUB_LIVE_CLAUDE=1` / `HUB_LIVE_CODEX=1` / `HUB_LIVE_OLLAMA=1`.
- **Orchestrator** (`app/orchestrator.py`): runs one turn per session in the background on its current stint, saves events (with `stint_id`), sets status and publishes to SSE listeners. `AdapterFactory` is `(session, stint, cwd) -> AgentAdapter`; `cwd` comes from `session_workdir` (the session's worktree plus its `subdir`, or `project_path`; a removed worktree raises `AgentUnavailable` naming the branch). A turn ending in `LIMIT_REACHED` (or a send to a stint whose last `RATE_LIMIT` says `rejected` and hasn't reset, which is how Codex's after-turn report is caught) goes to `_after_limit`: the next agent in the chain that the factory can build takes over (`auto`), or a `handoff_offer` event waits for the user (`ask`), or the session fails if none is left. `_handoff` ends the old stint, builds the brief, saves a `handoff` event and starts the new agent's first turn on the brief. Re-entering an agent always starts a fresh native session. `_limited_agents` keeps an automatic handoff from returning to an agent that hit its limit earlier in the same run (back through `limit` stints that never finished a turn), so a chain like Claude, Codex, Claude can't loop. With `HubSettings.chaining_enabled` off, `_after_limit` hands off to no one: it saves a `NOTICE` (`reason` `chaining_off`) and the session waits for input. A manual handoff (`POST /handoff`) takes `brief` (false: the new stint has no brief and starts clean, unless `messages` is true, which gives it only the user's own earlier messages via `messages_brief`) and `wait` (true: no turn starts, status goes to `ready`, the note is ignored, and the next `send` starts the agent on `with_brief(brief, text)`; `send` does that whenever the adapter has no native id yet and the stint has a brief); the `handoff` event carries `brief` and `waiting`. The UI's model picker always uses `wait`. `HUB_SIMULATE_LIMIT` (`Orchestrator.simulate_limit`, comma-separated agents) lets the real turn run and then replaces its `COMPLETED`/`QUESTION` with a `LIMIT_REACHED` marked `simulated`.
- **Worktrees** (`app/worktrees.py`, `Worktree` table): `POST /sessions` with `use_worktree` (default true) on a folder inside a git repo runs `git worktree add -b hub/<title-slug>-<id8>` from HEAD into `HUB_WORKTREES_DIR` (default `%LOCALAPPDATA%\MultiAgentHub\worktrees\<repo>-<id8>`). It must stay outside any repository, because Claude Code loads every `CLAUDE.md` above its cwd. A project subfolder maps to the same `subdir` inside the worktree. A repo with no commits is refused (400). `stint_id` is None for a whole-session worktree; phase 8 sets it for a child stint's own. `POST /sessions/{id}/worktree/remove` (`{commit, discard}`) refuses uncommitted changes with 409 `{message, changes}` unless told to commit them to the branch or discard them, then deletes the folder (or prunes it if the user already deleted it) and keeps the branch unless it has no commits beyond `base_commit`. Deleting a session removes its clean worktree and refuses a dirty one. `GET /folders/git?path=` tells the UI whether to offer the checkbox. Not a sandbox.
- **Chats**: `project_path` is optional on `POST /sessions`. Without it the session is a chat (`AgentSession.chat`, migration `95160a18dfff`, a plain `ADD COLUMN`): the hub makes an empty folder `HUB_CHATS_DIR/<session id>` (default `%LOCALAPPDATA%\MultiAgentHub\chats`, outside any repository) and stores it as `project_path`, so resume, handoff and summaries work unchanged (the CLIs resume only from the folder a conversation began in). No worktree. Deleting the session deletes the folder. The UI shows "Chat" instead of a folder, and the title defaults to the first message.
- **Handoff brief** (`app/handoff.py`): built by the hub from events plus `git status --short`, `git diff --stat HEAD` and `git diff HEAD` (no agent turns): task, later user messages, the previous agent's last 3 messages, a cut-off turn, files edited, last 20 commands, git, then the note or "continue". In a worktree the diff is against the branch's `base_commit`, so work the agents committed is included. Capped at 40k characters (diff 20k). `next_in_chain` picks candidates after the current agent.
- **Summaries** (`app/summary.py`, `AgentSummary` table `summaries`): the hub's own summary is built live in the UI (`SummaryPanel.tsx`) from events plus `GET /sessions/{id}/summary` (git status and diff stat, latest written summary, `summarizing`). `POST /sessions/{id}/summary` waits while `Orchestrator.summarize` gets a written one: a fresh adapter's `summarize(prompt, instructions)`, a one-off read-only call that never resumes or joins the session (Claude: `--no-session-persistence --tools "" --system-prompt`; Codex: `exec --ephemeral`, read-only sandbox). The current agent first, then the chain on a limit or `AgentUnavailable`; any other error is a 502. It saves the tokens used and `last_event_id`; `SummaryRead.outdated` is true once a `user_message` or `handoff` follows it. `SessionRead` carries `task` (first user message) and `summary` for the dashboard line.
- **API** (`app/api/`): routes under `/api`: health, folders, session CRUD (`PATCH /sessions/{id}` changes `title`, `limit_policy` and `chain`, only the keys sent, null meaning the Settings default, allowed mid-turn), `POST /sessions/{id}/messages`, `/stop`, `/handoff` (`{agent, model, note}`), `GET`/`POST /sessions/{id}/summary`, `GET /sessions/{id}/stints/{stint_id}` (with brief), `/events?after_id=N`, `/stream` (SSE), `GET/PUT /settings`, and `GET /usage` (each agent's latest usage windows from any session, since limits are per account). CORS allows the Vite dev server (port 5173) because the UI will run in a browser first.
