# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Multi-Agent Hub: a personal Windows desktop app that runs Claude Code, Codex and a local Ollama model as parallel agent sessions on different projects, with automatic handoff to the next agent when one hits a usage limit. `plan.md` is the confirmed plan (requirements, tradeoffs, build phases 1–9; phase 6, iPhone access, comes last). `progress.md` holds per-session recaps and the current next steps; read it first to see where work stopped, and append a new recap at the end of each session.

Phases 1–3 are done (Claude and Codex sessions, handoff, React UI in `frontend/`). Phase 4 is split into 4a–4d in `plan.md`: 4a (runner interface, per-session git worktrees) is built; 4b is built (dashboard, progress view, history and summaries; summaries await the user's check on a real session); 4c (style polish) and 4d (Tauri shell) are not started. The Ollama adapter (phase 5) is not built yet. Agents are driven through their official CLIs under the user's own logins; the app must never read or store login tokens.

## Commands

All from `backend/`, using `uv` (Python 3.14 pinned in `.python-version`, exact versions in `uv.lock`; commit `uv.lock`):

```powershell
uv sync                                          # install
uv run python -m app.main                        # run API on http://127.0.0.1:8765 (docs at /docs)
$env:HUB_RELOAD="true"; uv run python -m app.main   # dev auto-reload
$env:HUB_SIMULATE_LIMIT="claude"; uv run python -m app.main   # dev: Claude's turns end in a fake usage limit (try handoff)
uv run pytest                                    # all tests
uv run pytest tests/test_claude_adapter.py::test_name   # single test
$env:HUB_LIVE_CLAUDE="1"; uv run pytest tests/test_claude_live.py  # opt-in, uses real claude CLI + subscription usage
$env:HUB_LIVE_CODEX="1"; uv run pytest tests/test_codex_live.py    # opt-in, uses real codex CLI + ChatGPT Codex allowance
uv run alembic revision --autogenerate -m "describe change"  # after editing app/models.py; review the file
uv add <pkg> / uv add --dev <pkg>
```

Settings are `HUB_*` env vars or `backend/.env` (`HUB_DATABASE_URL`, `HUB_HOST`, `HUB_PORT`, `HUB_RELOAD`, `HUB_LOG_LEVEL`, `HUB_CORS_ORIGINS`, `HUB_WORKTREES_DIR`). The default DB is `backend/data/hub.db`.

## Architecture

- **App factory** (`app/main.py`): `create_app(engine=None)` builds the app; tests pass an in-memory `StaticPool` SQLite engine. Lifespan runs `init_db`, which applies Alembic migrations to `head` on every start, so there is no `create_all`. Schema changes always need a migration.
- **DB** (`app/db.py`, `app/models.py`): SQLModel on SQLite with foreign keys, WAL and busy_timeout set per connection. Tables: `sessions` (`AgentSession`: title, folder, status, optional per-session `chain` and `limit_policy`), `stints` (`Stint`: one agent's turn at a session with agent, model, native session id, `reason` new/limit/manual/delegation, optional `parent_stint_id` reserved for phase 7, and the `brief` it started from), `events` (`SessionEvent`, with `stint_id`) and `settings` (key/JSON value: `default_chain`, `limit_policy`). Child rows use `ON DELETE CASCADE`. The current stint is the latest by `seq` (`current_stint`); the API's `SessionRead` (`session_read`) exposes its agent, model and native id plus the stint list. Enums are stored by **value** as plain text with no CHECK constraint (`enum_column`), so adding a member needs no migration. Migrations use `render_as_batch=True` for SQLite, but **never batch-rebuild `sessions` or `stints`**: with foreign keys on, dropping the old table cascades and deletes child rows. Use plain `ALTER TABLE ADD/DROP COLUMN` (see the stints migration). Autogenerate reports a false `events.stint_id` FK change (SQLite reflection misses inline `ON DELETE`); drop it from generated files. `migrations/env.py` uses the connection passed in by `init_db` when there is one, and otherwise the settings URL (CLI).
- **Adapter interface** (`app/adapters/base.py`): one `AgentAdapter` instance per session, constructed with its cwd and model. `start_task` and `send_reply` return async iterators of normalized `AgentEvent`s (`EventType`). A usage limit is a `LIMIT_REACHED` **event**, not an exception, and handoff will key off it. The orchestrator, UI and history should depend only on this interface.
- **Claude adapter** (`app/adapters/claude.py`): one `claude -p --output-format stream-json --verbose` process per turn, with the prompt sent over **stdin** (this avoids Windows quoting). Replies use `--resume <session id>`. `--permission-prompts none` means unapproved tools are denied rather than left hanging. AskUserQuestion is unavailable headless, so an appended system prompt makes Claude end question turns with `[[NEEDS_INPUT]]`, which `TurnParser` turns into a `QUESTION` event. `rate_limit_event` with status `rejected` is the main limit signal; regex on the result text is the fallback. `stop()` kills the whole process tree (`taskkill /T`). It refuses `.cmd`/`.bat` shims and requires the native `claude.exe`. Behavior was verified against Claude Code 2.1.305.
- **Runner** (`app/adapters/runner.py`): every CLI launch goes through a `Runner` (`start(command, cwd, env)` returns a `RunningProcess` with `send_input`, `lines`, `read_stderr`, `wait`, `kill`). `HostRunner` (the default) runs a local process and kills its tree with `taskkill /T`. Phase 9's Docker runner plugs in here; adapters take an optional `runner=`.
- **Shared CLI plumbing** (`app/adapters/cli.py`): `CliAdapter` runs one process per turn through its runner, sends the prompt over stdin, streams parsed lines, adds an error if the CLI exits before reporting the end of the turn, and `stop()` kills the process tree. It also holds `NEEDS_INPUT_MARKER` / `HEADLESS_PROMPT` and the headless git env. Neither CLI has a plan tool headless, so `HEADLESS_PROMPT` asks for the plan as a markdown checklist under a `PLAN_MARKER` line, re-posted after each step; `split_plan` strips the marker from messages and both parsers turn the checklist into a `PLAN` event when it changes (`plan_items`: the first unchecked step is in progress). Both adapters subclass it.
- **Codex adapter** (`app/adapters/codex.py`): `codex exec --json -` per turn, `codex exec resume --json <thread id> -` for replies. Codex chooses the thread id and reports it in `thread.started`, so the adapter learns it from the stream and the orchestrator saves it from the `STARTED` event (Claude's id is chosen up front). Sandbox, `approval_policy="never"` and the marker instruction (`developer_instructions`) are passed as `-c` overrides, because `resume` has no `--sandbox`. `find_codex` runs the native `codex.exe` inside the npm package, never the `.cmd`/`.ps1` launchers. Exec mode never waits for approval: blocked actions fail as ordinary command errors. The stream has no rate-limit events, so after each turn `read_rate_limits` takes the plan's usage windows from the latest `token_count` in Codex's session file (`$CODEX_HOME/sessions/.../rollout-*-<thread id>.jsonl`, an undocumented format, read best effort) and emits the same `RATE_LIMIT` shape as Claude. A limit is detected from the error text. Codex reports no price, so the UI shows tokens. Verified against codex-cli 0.164.0. Settings: `HUB_CODEX_SANDBOX` (default `workspace-write`, which also allows `%TEMP%`) and `HUB_CODEX_PATH`.
- **Auth** (`app/auth.py`): every `/api` router is included with `Depends(require_caller)`, which checks `Authorization: Bearer` against the per-install token (`backend/data/token`, created in the lifespan, ACL'd to the current user) with `secrets.compare_digest` and returns a `Caller`. `HostOriginMiddleware` (outermost) rejects non-loopback `Host`, unknown `Origin`, and `Sec-Fetch-Site: cross-site`. `HUB_HOST` must be loopback. The Vite proxy injects the token, so the browser never holds it and `EventSource` still works. Tests use `make_client` in `conftest.py` (loopback `base_url` plus `TEST_TOKEN`); `create_app(..., token=)` skips the file.
- **Tests**: `tests/fake_claude.py` and `tests/fake_codex.py` stand in for the CLIs (modes `ok`, `question`, `crash`, `hang`; Codex also `tools`, `limit`) and are injected via `command=[sys.executable, FAKE_..., mode]`. `conftest.fake_adapter_factory(session, stint, cwd)` picks the fake by the stint's agent and the mode from the session title, either one mode (`ok`) or per agent (`claude:limit codex:ok`); Ollama raises `AgentUnavailable`. Fake Claude also has a `limit` mode and echoes its cwd. The `client` fixture puts worktrees in a temp folder; `test_worktrees.py` builds a real temp git repo. Live tests are opt-in: `HUB_LIVE_CLAUDE=1` / `HUB_LIVE_CODEX=1`.
- **Orchestrator** (`app/orchestrator.py`): runs one turn per session in the background on its current stint, saves events (with `stint_id`), sets status and publishes to SSE listeners. `AdapterFactory` is `(session, stint, cwd) -> AgentAdapter`; `cwd` comes from `session_workdir` (the session's worktree plus its `subdir`, or `project_path`; a removed worktree raises `AgentUnavailable` naming the branch). A turn ending in `LIMIT_REACHED` (or a send to a stint whose last `RATE_LIMIT` says `rejected` and hasn't reset, which is how Codex's after-turn report is caught) goes to `_after_limit`: the next agent in the chain that the factory can build takes over (`auto`), or a `handoff_offer` event waits for the user (`ask`), or the session fails if none is left. `_handoff` ends the old stint, builds the brief, saves a `handoff` event and starts the new agent's first turn on the brief. Re-entering an agent always starts a fresh native session. `_limited_agents` keeps an automatic handoff from returning to an agent that hit its limit earlier in the same run (back through `limit` stints that never finished a turn), so a chain like Claude, Codex, Claude can't loop. `HUB_SIMULATE_LIMIT` (`Orchestrator.simulate_limit`, comma-separated agents) lets the real turn run and then replaces its `COMPLETED`/`QUESTION` with a `LIMIT_REACHED` marked `simulated`.
- **Worktrees** (`app/worktrees.py`, `Worktree` table): `POST /sessions` with `use_worktree` (default true) on a folder inside a git repo runs `git worktree add -b hub/<title-slug>-<id8>` from HEAD into `HUB_WORKTREES_DIR` (default `%LOCALAPPDATA%\MultiAgentHub\worktrees\<repo>-<id8>`). It must stay outside any repository, because Claude Code loads every `CLAUDE.md` above its cwd. A project subfolder maps to the same `subdir` inside the worktree. A repo with no commits is refused (400). `stint_id` is None for a whole-session worktree; phase 8 sets it for a child stint's own. `POST /sessions/{id}/worktree/remove` (`{commit, discard}`) refuses uncommitted changes with 409 `{message, changes}` unless told to commit them to the branch or discard them, then deletes the folder (or prunes it if the user already deleted it) and keeps the branch unless it has no commits beyond `base_commit`. Deleting a session removes its clean worktree and refuses a dirty one. `GET /folders/git?path=` tells the UI whether to offer the checkbox. Not a sandbox.
- **Handoff brief** (`app/handoff.py`): built by the hub from events plus `git status --short`, `git diff --stat HEAD` and `git diff HEAD` (no agent turns): task, later user messages, the previous agent's last 3 messages, a cut-off turn, files edited, last 20 commands, git, then the note or "continue". In a worktree the diff is against the branch's `base_commit`, so work the agents committed is included. Capped at 40k characters (diff 20k). `next_in_chain` picks candidates after the current agent.
- **Summaries** (`app/summary.py`, `AgentSummary` table `summaries`): the hub's own summary is built live in the UI (`SummaryPanel.tsx`) from events plus `GET /sessions/{id}/summary` (git status and diff stat, latest written summary, `summarizing`). `POST /sessions/{id}/summary` waits while `Orchestrator.summarize` gets a written one: a fresh adapter's `summarize(prompt, instructions)`, a one-off read-only call that never resumes or joins the session (Claude: `--no-session-persistence --tools "" --system-prompt`; Codex: `exec --ephemeral`, read-only sandbox). The current agent first, then the chain on a limit or `AgentUnavailable`; any other error is a 502. It saves the tokens used and `last_event_id`; `SummaryRead.outdated` is true once a `user_message` or `handoff` follows it. `SessionRead` carries `task` (first user message) and `summary` for the dashboard line.
- **API** (`app/api/`): routes under `/api`: health, folders, session CRUD, `POST /sessions/{id}/messages`, `/stop`, `/handoff` (`{agent, model, note}`), `GET`/`POST /sessions/{id}/summary`, `GET /sessions/{id}/stints/{stint_id}` (with brief), `/events?after_id=N`, `/stream` (SSE), `GET/PUT /settings`, and `GET /usage` (each agent's latest usage windows from any session, since limits are per account). CORS allows the Vite dev server (port 5173) because the UI will run in a browser first.
